# HexGL — état actuel de l'architecture

Document descriptif, établi le 2026-10-22 par lecture du dépôt, mis à jour le même jour après la
personnalisation ACME de l'écran d'accueil. Il décrit l'état actuel uniquement.
Les chemins sont relatifs à `HexGL/`, dossier qui contient `index.html`.

**Méthode et limites.** Les constats viennent de la lecture du code. Le lancement et la course ont été
exécutés dans Chrome headless (menu, compte à rebours, course accélérée), sans erreur JS observée. La fin
de course, la fin de partie et le mode replay n'ont pas été atteints : les constats qui les concernent
sont statiques et non vérifiés à l'exécution.

## 2. Flux principal de lancement

Ordre observé, de `index.html` à la course.

1. **Chargement des scripts** — `index.html:92-132` charge dans l'ordre : bibliothèques (`libs/`),
   utilitaires (`bkcore.coffee/`), couche threejs (`bkcore/threejs/`), audio (`bkcore/Audio.js`),
   modules HexGL (`bkcore/hexgl/*.js`), `branding/branding.js` (l. 130), puis `launch.js` en dernier.
   Au chargement, `branding.js` applique sa configuration au DOM : logo en `background-image` inline sur
   `#title`, nom et message dans `#brand-block` (`index.html:50-53`, caché par défaut), couleurs en variables
   CSS posées sur `<html>`. `launch.*` n'intervient pas dans cette étape.
2. **Menu** (`step-1`, `index.html:46-64`) — `launch.js` lit les réglages de menu (Controls, Quality, HUD,
   Godmode) avec une valeur par défaut. Une valeur peut être forcée par un paramètre d'URL (`launch.js:45-53`,
   via `bkcore.Utils.getURLParameter`).
3. **Clic sur START** — `launch.js` (`$('start').onclick`) masque `step-1` et affiche `step-2`, l'aide
   contrôles (image `css/help-N.png`).
4. **Clic sur l'aide** (`step-2`) — appelle `init(controlType, quality, hud, godmode)` (`launch.js:9-37`) :
   instancie `bkcore.hexgl.HexGL` puis appelle `hexGL.load({onLoad, onProgress, onError})`.
5. **Chargement** — affiche `step-3` (barre `progressbar`). `HexGL.prototype.load` (`HexGL.js:151`) passe au
   loader (`bkcore/threejs/Loader.js`).
6. **Fin de chargement** (`onLoad`, `launch.js:17-22`) — `hexGL.init()` (`HexGL.js:140`), affiche `step-4`
   (`overlay` + `main`), puis `hexGL.start()` (`HexGL.js:92`).
7. **Course** — `initGameplay` (`HexGL.js:156`) crée `bkcore.hexgl.Gameplay` (`HexGL.js:160`). Le jeu
   tourne dans une boucle `update` (`HexGL.js:130`) ; `Gameplay` applique le mode (`Gameplay.js:211`,
   `this.modes[this.mode].call(this)`), par défaut `timeattack`.
8. **Fin** — `Gameplay.end` (`Gameplay.js:158`) déclenche `onFinish`, qui appelle `displayScore`
   (`HexGL.js:181`) et affiche `step-5` (« Click/Touch to continue ») ; le clic recharge la page
   (`launch.js`, `$('step-5').onclick`).

### 3.3 Décisions techniques durables (branding)

- **Un seul point de configuration** : l'objet `bkcore.Branding.config` dans `branding/branding.js`.
  `null` ou vide conserve l'apparence d'origine ; `enabled: false` n'applique rien ; un élément absent du
  document est ignoré.
- **Convention CSS** : une valeur fixe, suivie de la même couleur lue par `var(--brand-*, valeur d'origine)`,
  pour les anciens navigateurs. Variables : `--brand-menu` (`css/multi.css:126`, `:179`), `--brand-accent`
  (`:153`, `:161`), `--brand-accent-hover` (`:166`).
- **Pas de variable pour le fond** : le fond de l'accueil est une image (`css/bg.jpg`).
- **Code du jeu intact** : `launch.*`, `bkcore/` et `libs/` ne sont pas modifiés. Le branding s'applique par
  un script séparé chargé avant `launch.js`.
- **Logo sous `branding/`** et non lu depuis `formation/`, dossier de matériel de formation.

## 4. Dépendances et zones legacy à risque

### 4.1 Dépendances

- **Three.js r50dev** (`libs/Three.dev.js`) et passes `libs/postprocessing/*` (EffectComposer, Bloom, Film, etc.).
- **leap-0.4.1** (`libs/leap-0.4.1.min.js`) : utilisé par `ShipControls.js` pour le contrôleur Leap Motion.
- **Fichiers présents mais peu ou pas utilisés** : `libs/DAT.GUI.min.js`, `libs/Stats.js`, `libs/Editor.html`
  et `libs/Editor_files/` (éditeur de scène, aucun lien depuis le jeu), `libs/Three.r53.js` (référencé
  seulement par `bkcore.coffee/tests.html`, page ancienne qui n'est pas un test QUnit).
- **Google Analytics** `ga.js` avec le compte `UA-26274524-4` (`index.html:35-40`).
- **Ressources externes** : favicon `http://hexgl.bkcore.com/favicon.png` (`index.html:13-14`), liens de
  partage Twitter et Facebook (`HexGL.js`, dans `displayScore`).
- **QUnit 2.26.0** (`formation/tests/vendor/`), en local.
- **Aucun gestionnaire de paquets** : pas de `package.json`, pas de lockfile, versions figées dans `libs/`.
  Le branding n'ajoute aucune dépendance.

### 4.3 Bugs et anomalies remarquables

Les constats « statique » n'ont pas été reproduits à l'exécution.

1. **`bkcore/hexgl/HexGL.js:228` — `JSON.Stringify`** (statique). La fonction s'appelle `JSON.stringify`.
   Ce code s'exécute à la fin d'une course gagnée, quand le score est un nouveau record local ou qu'il
   n'existe pas encore. Il lèverait une `TypeError`.
2. **`bkcore/hexgl/HexGL.js:236` — `bkcore.hexgl.Ladder.global[t][d]`** (statique). `Ladder.global` est
   initialisé à `{}` (`Ladder.js:12`), et `Ladder.load` n'est appelé nulle part (aucun appel trouvé par
   recherche textuelle). `global[t]` est donc `undefined` et l'accès `[d]` lèverait une `TypeError`, à
   chaque fin de course gagnée. Le même bloc appelle `displayLadder` (`HexGL.js:273`).
3. **`bkcore/hexgl/Gameplay.js:101` — `self.result.REPLAY`** (statique). `result` est un nombre
   (`Gameplay.js:44`) : la constante est `self.results.REPLAY`. La valeur passée à `end` est donc `undefined`.
4. **Espace de noms incohérent dans `Ladder.js`** (statique). La définition utilise `bkcore.hexgl.Ladder`
   (lignes 11-12, 33) mais les accès utilisent `bkcore.Ladder` (lignes 20, 36, 42). Les accès ne sont
   pas résolus ; celui de la ligne 20 est dans un `try` qui avale l'erreur et écrit un `console.warn`.
5. **Garde inefficace dans `Ladder.js:36`** (statique) : `!bkcore.Ladder.global[track][mode] == undefined`
   vaut toujours `false`, car `!x` est un booléen comparé à `undefined`.
6. **Requête fantôme dans `Ladder.js:17`** : `bkcore.Utils.request("nothing", ...)` interroge un fichier
   `nothing` qui n'existe pas dans le dépôt.
7. **`bkcore.coffee/Utils.js`, `request`** (statique). Pour une requête GET, `data` n'est jamais ajouté à
   l'URL (l'ajout n'a lieu que si `postData != null`). En POST, la boucle ajoute `?qdata` à l'URL à
   chaque clé.
8. **`bkcore.coffee/Utils.js`, `getURLParameter`** (statique). Le cache est stocké sur `this`. `launch.js:45`
   l'appelle détachée (`u = bkcore.Utils.getURLParameter`) : en mode non strict, `this` est `window`, et
   `URLParameters` devient une propriété globale.
9. **`bkcore/hexgl/Gameplay.js`, `simu`** (~ligne 107). Fonction qui fixe des temps de tour en dur
   (`92300, 91250, 90365`) et force la fin. Aucun appelant trouvé : code mort ou outil de test oublié.
10. **Mode `replay`** (`Gameplay.js:95`) : défini, mais aucun appel `mode: "replay"` trouvé dans
    `bkcore/hexgl/`.
11. **Personnalisation ACME** (`formation/tickets/company-event.md`) : le logo ACME et le nom « ACME » sont
    appliqués à l'écran d'accueil par `branding/branding.js`. Les couleurs de charte (`colors.*`) et le
    message d'accueil (`welcome`) sont à `null` : le PDF de charte n'a pas de texte extractible et le
    message n'est pas fourni.

## 5. Fonctions et modules testables automatiquement

### 5.1 Tests QUnit existants (`formation/tests/browser-tests.js`)

Dix-huit tests, 52 assertions :

- **`bkcore.Utils`** (7) : `updateClass` (ajout, suppression), `getOffsetTop` (parent/enfant avec objets
  simulés, cas sans parent), `getURLParameter` (lecture d'un paramètre, paramètre absent ; le résultat
  attendu dépend de `window.location`), `isTouchDevice` (renvoie un booléen).
- **`bkcore.Timer`** (7) : `msToTime`, `msToTimeString`, `zfill`, `getElapsedTime`, `start`/`pause`,
  `update` sans effet sur un timer inactif.
- **`bkcore.Branding`** (4) : `enabled` à `false` n'applique rien, valeurs à `null` sans effet,
  configuration complète appliquée (logo, textes, variables de couleur), nom sans message.

`formation/tests/index.html` charge `Utils.js`, `Timer.js` et `branding/branding.js`. La page valide le
résultat si `data-test-status="pass"` et si QUnit compte au moins 4 assertions (`browser-tests.js`,
`QUnit.done`) ; le libellé « test(s) » du résumé affiche en réalité ce nombre d'assertions.

Exécution automatique : `formation/tests/ci-chrome.sh` (Linux) et `ci-chrome.bat` (Windows), codes de
retour 0 / 1 / 2 selon `formation/tests/README.md`. Le script n'affiche pas le nombre de tests : il se lit
dans le DOM (`data-test-count`, `data-test-failures`).
